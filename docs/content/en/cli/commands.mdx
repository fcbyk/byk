# Options & Commands

byk's command line has only three layers: **options**, **aliases**, and the **program interface**. Apart from the words in [Reserved Words](#reserved-words), every word is treated as an alias to look up — so you can name aliases whatever you like.

```
Usage: byk [OPTIONS] [ALIAS] [ARGS]...
```

## Options

| Option | Description |
|--------|-------------|
| `-h, --help` | Help: banner + Usage + Options + aliases in the merged space |
| `-v, --version` | Version, build info, and install path |
| `--paths` | Print the directories the CLI uses |

Running `byk` with no arguments produces exactly the same output as `byk -h`. The first line is always `byk <version> (<commit> <build date>) [<platform>]`, so you can safely grab the version with `byk -v | head -1`.

```bash title="-v"
$ byk -v
byk 0.6.0 (a1b2c3d4e 2026-11-08) [darwin-arm64]
installed at /opt/homebrew/bin/byk
```

```bash title="--paths"
$ byk --paths

CLI Home: /Users/coke/.byk
Alias: /Users/coke/.byk/alias
```

`CLI Home` is byk's home directory and `Alias` is where global alias files live — drop `*.byk.json` files there and they join the `byk <key>` lookup space.

The alias list in the help page covers the **merged space** only: aliases marked `$private: true` never appear, since they are reachable through `@file.key` alone. An alias with a `$cwd` gets its effective directory appended, as in `deploy  deploy.sh (/Users/me/proj)`.

## Running Aliases

| Form | Description |
|------|-------------|
| `byk <key> [args...]` | Look up and run from the merged alias space |
| `byk @file.key [args...]` | Run an alias from a specific file in the **current directory** |
| `byk @@file.key [args...]` | Run an alias from a specific file in the **global directory** `~/.byk/alias/` |

The merged space consists of the global directory `~/.byk/alias/` (priority 0) and the current directory (priority 1); on name collisions, the project's alias wins.

```bash
byk dev                  # merged-space lookup (project takes priority)
byk @run.build           # build from ./run.byk.json
byk @@work.deploy        # deploy from ~/.byk/alias/work.byk.json
```

The exact syntax is pure file routing with no fallback: a missing file reports `Alias file not found: @run` (`@@run` for the global side), a missing key reports `Alias key not found in file @run: build`, and both exit with code 1.

## The `__api__` Program Interface

`byk __api__` is a read-only interface for programs and editor plugins: **it never executes an alias and never writes to disk**, so you can call it as often as you like. It does not appear in `-h`.

```bash
byk __api__              # interface manifest (don't memorise request names)
byk __api__ paths root   # one directory, unparsed
```

The request list, the meaning of every field and worked examples live in [Program Interface](/cli/api) — that is the page to read when integrating.

## Reserved Words

Every word after `byk` is treated as an alias, with only these exceptions — none of them can be an alias name:

| Reserved | Why |
|----------|-----|
| `-h` / `--help` | Option |
| `-v` / `--version` | Option |
| `--paths` | Option |
| `__api__` | Hidden interface |

Everything else is free — even words like `version` or `paths` work as aliases, as long as they do not start with `-`.

## Match Order

When you run `byk <word> ...`, the following order applies — the first match wins:

1. The `__api__` hidden interface
2. Options such as `-h` / `-v` / `--paths`
3. `@file.key` / `@@file.key` exact execution
4. Aliases in the merged space

When nothing matches, byk prints `Unrecognized command or alias: <word>` along with candidate suggestions and exits with code 1.
