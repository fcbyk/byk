# Alias Configuration

## Type Definitions

```ts title="alias.types.ts"
// Alias object (the metadata-carrying form)
type AliasObject = {
  $cmd?: string;
  $cwd?: string;
  $mode?: 'normal' | 'interactive' | 'silent';
  $description?: string;
  $recursive?: boolean;
  $private?: boolean;
  [key: string]: string | AliasObject | boolean | undefined;
}

// A single *.byk.json file: an alias object, or a one-entry link array
type AliasFileJSON =
  | {
      $priority?: number;      // ordering priority; defaults to 1 in the current directory, 0 globally; negatives become 0
      $cwd?: string;           // file- or group-level working directory, inherited by child aliases
      $mode?: 'normal' | 'interactive' | 'silent';  // file- or group-level mode, inherited by child aliases
      $private?: boolean;      // file- or group-level visibility, inherited by child aliases; private aliases stay out of the merged space
      $paths?: string[];       // file-level PATH directories, inherited by child aliases
      $var?: Record<string, string | Record<string, string>>;  // file-level variables
      [key: string]: string | AliasObject | number | boolean | undefined;
    }
  | [string];  // single link: an array holding exactly one path
```

Only these six `$`-prefixed keys are recognized; any other `$xxx` is passed through to the shell verbatim (or expanded by [variables](#variables)).

## Alias Objects

### Key Naming Rules

- A key **cannot contain** `@` or `.`; violating entries are silently ignored
- Chinese key names are supported
- Nested groups (objects) are supported and accessed with the `.` separator

```json title="chinese-keys.byk.json"
{
  "开发": {
    "测试": "pytest -q",
    "构建": "pnpm run build"
  }
}
```

```bash
byk 开发.测试
```

### System Fields

| Field | Type | Description |
|-------|------|-------------|
| `$cmd` | string | The command to execute |
| `$cwd` | string | Working directory (inheritable) |
| `$mode` | `'normal'` \| `'interactive'` \| `'silent'` | How to run the alias (inheritable), defaults to `normal` |
| `$description` | string | Help-page description text (not inheritable) |
| `$recursive` | boolean | Allow re-entering this alias on the call chain (not inheritable), defaults to `false` — see [Recursion Guard](#recursion-guard) |
| `$private` | boolean | Keep this subtree out of the merged space, reachable only through exact calls (inheritable), defaults to `false` — see [Visibility](#visibility) |

:::note
An object containing `$cmd` is an alias leaf node. An object with only `$cwd` / `$mode` / `$private` but no `$cmd` is a **group with inherited properties** and is not executable itself.
:::

### Working Directory (cwd)

Three levels of inheritance: file → group → alias, with the level closer to the alias winning. `~` expands, and **a relative path is resolved against the alias file's directory** — not the directory you happened to run `byk` from. With no `$cwd` at all, the alias runs in the invocation directory.

<Tabs>
<Tab label="Alias level">

```json
{
  "install": {
    "$cmd": "npm i",
    "$cwd": "/project/web"
  }
}
```

</Tab>
<Tab label="Group level">

```json
{
  "services": {
    "$cwd": "/project",
    "install": "npm i",
    "web": {
      "$cwd": "/project/web",
      "dev": "pnpm dev",
      "build": "pnpm build"
    }
  }
}
```

`install` inherits `/project` from `services`, while `web.dev` and `web.build` use the `/project/web` override from the `web` group.

</Tab>
<Tab label="File level">

```json
{
  "$cwd": "/project/web",
  "install": "npm i",
  "start": {
    "$cmd": "pnpm dev",
    "$cwd": "/project/web/frontend"
  }
}
```

`install` inherits the file-level `/project/web`, while `start` uses its own `/project/web/frontend`.

</Tab>
</Tabs>

### Execution Mode

`$mode` decides how an alias runs. The three states are mutually exclusive and `normal` is the default.

| Value | Behavior |
|---|---|
| `normal` | Print the hint lines, then run directly |
| `interactive` | Print the hint lines, ask for each placeholder, then wait for Enter |
| `silent` | Say nothing even on a terminal (a pipe already gets nothing) |

Before running, byk prints two lines to **stderr**: the source (`file.key` plus the working directory) and the resolved command. They belong there because they are commentary for a human, not data to be piped:

- `byk build > log.txt` and `byk build | grep error` receive only the command's own output;
- when stderr is not a terminal (redirected with `2>`, CI, editor tasks) the two lines are skipped entirely;
- `$mode: "silent"` is for staying quiet on a terminal as well.

```bash
byk build
# > @.build /project
#
# > pnpm build
#
# ...(output of pnpm)

# with "$mode": "silent"
byk build
# ...(output of pnpm only)
```

`interactive` fits commands with side effects:

```bash
byk deploy
# ~ deploy --env {env} --tag {version}
#   env: staging
#   version: v2.0
# ~ deploy --env staging --tag v2.0     ← bold green
#    Press Enter to execute...
```

`$mode` inherits through three levels — file, group, alias — with the closest one winning.

<Tabs>
<Tab label="Alias level">

```json
{
  "deploy": {
    "$cmd": "deploy --env {env} --tag {version}",
    "$mode": "interactive"
  }
}
```

</Tab>
<Tab label="Group level">

```json
{
  "danger": {
    "$mode": "interactive",
    "drop": "rm -rf {path}",
    "backup": {
      "$cmd": "rsync -a ./ {dest}",
      "$mode": "silent"
    }
  }
}
```

`drop` inherits the interactive mode from `danger`; `backup` just says `silent` — there is no second switch to turn off.

</Tab>
<Tab label="File level">

```json
{
  "$mode": "silent",
  "build": "pnpm build",
  "deploy": {
    "$cmd": "deploy --env {env}",
    "$mode": "interactive"
  }
}
```

The whole file stays quiet; only `deploy` asks for confirmation.

</Tab>
</Tabs>

:::note
Interactive and silent are the two extremes of one axis: interactive has to show what is about to run, so `silent` merely keeps byk quiet — it never skips a confirmation step. Reach for `interactive` when a command needs one.
:::

### Recursion Guard

`$cmd` is an arbitrary shell string, so it can invoke byk again — including resolving back to itself. Give the `add` alias a `$cmd` of `byk add` and every level re-expands the same alias; each level is its own process, so there is no stack to overflow, only a process count that keeps climbing until the machine gives up.

byk therefore leaves a trail on the call chain: before running an alias it pushes `file.key` onto the `BYK_ALIAS_STACK` environment variable (comma-separated) and hands it to the child process. A level that finds itself already on the chain reports and exits:

```text
Error: alias recursion detected: @dev.build -> @dev.release -> @dev.build
```

The **whole chain** is printed, not just the endpoints — which level looped back is the thing worth locating. Chains deeper than 32 levels are stopped as well: that backstop exists for wrappers that scrub the environment (`env -i byk build`), where the trail cannot survive and depth is all that is left.

Deliberate self-invocation (`FOO=1 byk build`, `sudo byk serve`) needs an explicit opt-in; these two are equivalent:

```json
{
  "build": {
    "$cmd": "FOO=1 byk build",
    "$recursive": true
  }
}
```

```bash
BYK_ALLOW_RECURSION=1 byk build   # temporary, global
```

Opting in only disables the "same alias re-entered" check; the depth limit still applies.

:::note
`$recursive` applies to the current alias only and is not inherited. `$mode: "silent"` does not suppress this error either — explaining why a command hung is exactly what it is for.
:::

### Description Text

`$description` replaces the command text shown by default in the help page. It applies to the current alias only and is not inherited.

```json
{
  "release": {
    "$mode": "interactive",
    "$cmd": "cz bump {version}",
    "$description": "Bump the version interactively"
  }
}
```

```text title="byk -h excerpt"
Aliases:
  release    Bump the version interactively
```

When unset, the command itself is shown:

```text
Aliases:
  release    cz bump {version}
```

A resolved `$cwd` is appended in parentheses only when no description is set — with a description, the line stays a single summary and the working directory is left out.

### PATH Directories

`$paths` prepends directories to `PATH` before an alias runs, letting the alias call executables in those directories directly.

**File level only** — all child aliases inherit it; writing it inside a group is ignored.

```json title="run.byk.json"
{
  "$paths": ["./scripts", "~/tools/bin"],
  "deploy": "deploy.sh",
  "check": "lint.sh"
}
```

- Relative paths are resolved against the directory containing the config file, and `~` expands
- **Nonexistent directories are silently skipped** — they never reach the child process's `PATH`
- Separately, byk always prepends the working directory's `node_modules/.bin`; there is no need to write it into `$paths` yourself
- The order of `$paths` is the order in `PATH`, so earlier entries win

### Variables

Variables come from two places and are merged into **a single table**, substituted once during the scan phase:

| Source | Description |
|--------|-------------|
| Built-in | `${byk_dir}` → `~/.byk` (the resource root, not the binary directory); `${file_dir}` → the directory holding the current alias file |
| `$var` declarations | File-scoped custom variables |

On a name collision, **the file declaration wins** — the value you wrote explicitly is the value you get.

The syntax is uniformly `${name}`, where `name` matches `[A-Za-z_][A-Za-z0-9_]*` (the same rule as shell identifiers):

```json title="run.byk.json"
{
  "$var": {
    "BASE": "https://github.com/owner/repo/releases/download",
    "VER": {
      "darwin-arm64": "tool-mac",
      "linux-x86_64": "tool-linux"
    }
  },
  "fetch": "curl -fsSL ${BASE}/${VER} -o /tmp/tool",
  "log": "tail -f ${byk_dir}/logs/app.log"
}
```

| Rule | Description |
|------|-------------|
| Syntax | `${name}` — the braces are the delimiter and are required |
| Bare `$xx` | Not recognized; passed to the shell as-is (`$HOME`, `$PATH` are still expanded by the shell) |
| Scope | File-level: applies to all string values including `$cmd` / `$cwd` / `$paths`; JSON keys are untouched |
| Override | A `$var` entry with a built-in's name takes that built-in's place |
| Self-reference | In `"byk_dir": "${byk_dir}/tools"` the right-hand side is the built-in value, yielding `~/.byk/tools` |
| Escaping | `\${byk_dir}` is passed to the shell untouched, printing the literal `${byk_dir}` |
| Platform mapping | A value can be a platform map (`linux-x86_64` / `linux-arm64` / `darwin-x86_64` / `darwin-arm64` / `windows-x64`); the current platform's value is used |
| Cross-references | Values may reference each other regardless of declaration order, for at most 8 rounds |
| Undefined | `${XXX}` is kept as-is; `args` is reserved for placeholders and its declaration is ignored |
| Invalid names | Names that are not valid identifiers are ignored with a warning on stderr |

:::tip Why the braces are mandatory
A bare `$byk_dir` has no terminator: there is no way to tell whether `$byk_dirfoo` means the variable `byk_dirfoo` or `byk_dir` followed by `foo`. `${byk_dir}foo` has no such ambiguity — which is also why it matches the shell syntax you already know.
:::

**Quoting is your job**: when a value contains whitespace, wrap it in quotes per shell rules; byk will not do it for you.

```json title="run.byk.json"
{
  "log": "tail -f \"${byk_dir}/my logs/app.log\"",
  "where": "echo ${file_dir}"
}
```

`${file_dir}` is the directory **holding the alias file** — neither the directory an alias `$cwd` points at, nor the one `byk` was invoked from. Reach for the shell's `$PWD` when you need the latter.

## Alias Files

byk reads two locations: the **global directory** `~/.byk/alias/` and the **current working directory** (non-recursive).

### File Naming

| Format | Example | Description |
|--------|---------|-------------|
| `[name].byk.json` | `run.byk.json` | Recommended form; the name is the file key |
| `.byk.json` | `.byk.json` | Anonymous form; the key is an empty string |

:::warning
**Legal characters**: letters, digits, `-`, `_`, and Chinese characters.

**Forbidden characters**: `.`, `@`, `/`, and spaces.

Illegally named files (such as `aaa.bbb.byk.json`) are **silently skipped** — no error is raised.
:::

### Directory Layout

```tree
# global
~/.byk/alias/
├── alias.byk.json
├── work.byk.json
└── .byk.json
```

```tree
# current directory
./
├── run.byk.json
├── release.byk.json
└── .byk.json
```

### Single Link

When the root is an **array holding one path**, the file is a link file: a pointer to another alias file:

```json title="~/.byk/alias/ops.byk.json"
["~/proj/web/run.byk.json"]
```

The link file gives up its own identity: the `@` / `@@` prefix, its key and its default priority stay with the link file, while the aliases and every declaration come from the target — and relative paths resolve against the **target's** directory. The same bundle therefore behaves identically whether it is scanned directly or reached through a link.

```json title="~/proj/web/run.byk.json"
{
  "$cwd": ".",
  "build": "node build.js",
  "deploy": "node deploy.js"
}
```

```bash
byk build           # runs node build.js inside ~/proj/web
byk @@ops.build     # exact call goes through the link's key
```

| Rule | Behavior |
|---|---|
| One entry only | Extra entries are ignored with a note on stderr; the first is used |
| Path base | Relative paths resolve against the **link file's** directory; `~` and `${...}` work |
| One level | The target may not itself be an array; that is an error and the file is skipped |
| Identity | Key, `@` / `@@` prefix and default priority come from the link; everything else from the target |
| `$private` | Still honoured: a target with `true` pulls the link out of the merged namespace, leaving exact calls only |

:::note
A missing target, broken JSON or an empty array only skips that one file — other aliases keep working.
:::

### Priority

All merged files share a single key space, and higher-priority files override lower-priority ones.

#### Defaults

| File location | Default priority |
|---------------|------------------|
| Current directory `[name].byk.json` | 1 |
| Current directory `.byk.json` | 1 (loads last among its peers) |
| Global `[name].byk.json` | 0 |
| Global `.byk.json` | 0 (loads last among its peers) |

Hence "near-first": project files automatically override same-named global aliases, so `byk <key>` works the moment you enter a directory — no declaration needed.

Files at the same priority load in alphabetical order by filename, and the anonymous `.byk.json` sorts **last** among its peers; later files override earlier ones. So if both `a.byk.json` and `.byk.json` in one directory define `build`, the `.byk.json` copy is the one that runs.

:::note Running inside the global directory
When the cwd happens to be `~/.byk/alias/`, the files there belong to both the "current directory" and the "global directory". They are scanned in both roles (`@f` and `@@f` both work), but they participate in the merge **only once, as the global role** — they are never merged twice.
:::

#### Custom Ordering

Only write a number when you need to outrank other files in the same directory:

```json title="any .byk.json"
{
  "$priority": 20,
  "build": "vite build"
}
```

`$priority` only orders same-name collisions; values below 0 are treated as 0. Whether a subtree enters the merged space is controlled by `$private`.

:::note
`$priority` is a reserved field and is never treated as an alias key. When omitted, the current directory uses 1 and the global directory uses 0.
:::

### Visibility

`$private: true` keeps a subtree **out of the merged space**; it stays reachable through exact syntax `@file.key` / `@@file.key`.

Like `$cwd` and `$mode`, it has three levels of inheritance: file → group → alias, with the closest level winning. A child can set `false` to expose its subtree again.

```json title="run.byk.json"
{
  "shared": "echo everyone-can-run-this",
  "scratch": {
    "$private": true,
    "deploy": "deploy --env {env}"
  }
}
```

`byk shared` still works; `byk scratch.deploy` is not found and only `byk @run.scratch.deploy` reaches it.

To keep a whole file out of the merged space, put `$private` at the file root:

```json title="local.byk.json"
{
  "$private": true,
  "deploy": "deploy --env {env}"
}
```

:::note
`$private` only affects the merged space; exact calls always work, including aliases inside a private group.
:::

### Exact Execution Syntax

| Syntax | Description |
|--------|-------------|
| `byk @release.build` | `build` from `release.byk.json` in the current directory |
| `byk @@release.build` | `build` from `~/.byk/alias/release.byk.json` |
| `byk @.build` | `build` from the anonymous `.byk.json` in the current directory |
| `byk @@.build` | `build` from the anonymous `.byk.json` globally |

Conventions:

- Pure file routing, no fallback
- File not found → `Alias file not found: @release` (`@@release` on the global side)
- File exists but key not found → `Alias key not found in file @release: build`
- Both cases exit with code 1
